# Internationalization (i18n) Skill

## Purpose

This Skill defines how translated strings must be structured and consumed in this project, using `i18next` + `react-i18next`, so that every feature follows the same pattern instead of each one inventing its own.

It does not cover language detection/switching strategy — that lives in `src/i18n/index.ts` — only how to add and consume translations correctly once that setup exists.

---

# Mandatory: No Hardcoded Text

**Every piece of user-facing text in the app must come from an i18n translation key. Literal strings are not allowed anywhere a user can see them.**

This applies to every kind of user-facing text, not just obvious "content" — including but not limited to:

- labels, titles, and descriptions
- button and link text
- `placeholder`s
- Zod validation/error messages
- empty states, toasts, alerts, and dialog copy
- `accessibilityLabel`/`accessibilityHint` and other accessibility strings (see [`a11y.md`](a11y.md) for when those are required)
- option lists (dropdown/segmented-button options, etc.)

The only text that's exempt is text that is never shown to a user: `testID`s, internal `console.log`/`console.warn` debug messages, code comments, and non-visual identifiers/keys.

Bad:

```tsx
<AppButton mode="contained" onPress={handleSubmit(onSubmit)}>
  Registrar medicamento
</AppButton>
```

Good:

```tsx
const { t } = useTranslation("medications");

<AppButton mode="contained" onPress={handleSubmit(onSubmit)}>
  {t("scheduledForm.submit")}
</AppButton>
```

When writing or reviewing any component, screen, or constants file, a literal user-facing string sitting directly in the code is always a defect — route it through `t()` following the patterns below (inside a component via `useTranslation`, outside a component via `t("namespace:key")` imported from `@/i18n`) instead of leaving it inline, even for something that feels trivial (a single word, a placeholder, a temporary label). There is no "add the translation later" — every new string ships already translated in both `en` and `es`.

# File Structure

```
src/i18n/
  index.ts                 # i18next init, exports `t` and the default `i18n` instance
  types.d.ts                # module augmentation so t()'s keys/namespaces are typed
  locales/
    index.ts                # aggregates { es, en } into the `resources` i18next receives
    en/
      index.ts               # re-exports every namespace for this language
      common.json
      profile.json
      medications.json
    es/
      index.ts               # same namespaces, same keys, translated
      common.json
      profile.json
      medications.json
```

**One JSON file per feature = one i18next namespace.** `profile.json` is the `profile` namespace, `medications.json` is the `medications` namespace, etc. There is no per-component file — a feature's strings live in its namespace file regardless of how many components under that feature use them.

---

# Adding a New Namespace

1. Create `ComponentName.json` — actually `<namespace>.json` — under **both** `src/i18n/locales/en/` and `src/i18n/locales/es/`, with the exact same key structure in each.
2. Import and re-export it from both `src/i18n/locales/en/index.ts` and `src/i18n/locales/es/index.ts`:

```ts
// src/i18n/locales/en/index.ts
import common from "./common.json";
import medications from "./medications.json";
import profile from "./profile.json";

export { common, medications, profile };
```

That's it — `src/i18n/locales/index.ts` already aggregates whatever `en`/`es` export (`export const translations = { es, en };`), and `types.d.ts` derives its typed keys from `typeof en`, so a new namespace becomes fully typed in `t()` calls automatically. Never add a namespace to only one language, and never let the two files' key structures drift apart — `fallbackLng` is `"en"`, so a key missing from `es` will silently fall back to the English string rather than error.

# Using Translations Inside Components

Use `useTranslation(namespace)` and call `t()` with the key relative to that namespace:

```tsx
import { useTranslation } from "react-i18next";

const { t } = useTranslation("profile");

t("onboardingRegister.form.fullName");
```

Nest keys by screen/section, not by flattening everything — e.g. `onboardingRegister.form.sexOptions.female`, not `onboardingRegisterFormSexOptionsFemale`. This keeps the JSON file organized the same way the JSON structure reads, and keeps related strings (a form's fields, a form's options) grouped together.

---

# Using Translations Outside Components

A module-level constant (e.g. a `ComponentName.constants.ts` options array) can't call the `useTranslation` hook. Import `t` directly from `@/i18n` and prefix the key with the namespace and a colon:

```ts
import { t } from "@/i18n";

export const SEX_OPTIONS = [
  { label: t("profile:onboardingRegister.form.sexOptions.male"), value: "male" },
  // ...
];
```

This resolves once, at import time, using whatever language is active then — it is **not reactive** to a later language change or to any other runtime value (like a `count` for pluralization). Anything that needs to react to state (the current language, a live form value) must be computed inside a component's render, not baked into a module-level constant.

---

# Pluralization

i18next resolves plural forms automatically via key suffixes when you pass a `count` option — define `<key>_one` and `<key>_other` (the two CLDR categories both Spanish and English use) side by side in the JSON, and call `t(key, { count })`:

```json
{
  "doseUnits": {
    "tablet_one": "Tableta",
    "tablet_other": "Tabletas",
    "ml": "mL"
  }
}
```

```ts
t("doseUnits.tablet", { count: 1 }); // "Tableta"
t("doseUnits.tablet", { count: 2 }); // "Tabletas"
t("doseUnits.ml", { count: 5 });     // "mL" — no _one/_other defined, falls back to the plain key safely
```

A unit that never changes form (like `mL`) doesn't need `_one`/`_other` — passing `count` to a key with no plural forms is harmless; i18next just returns the base key's value.

When a label needs to pluralize against a **live** value (e.g. a quantity the user is typing into a React Hook Form field), don't precompute it into a module-level constant — watch the field and recompute inside the component:

```tsx
const { t } = useTranslation("medications");
const doseQuantity = useWatch({ control, name: "doseQuantity" });

const doseUnitOptions = DOSE_UNIT_KEYS.map((key) => ({
  label: t(`doseUnits.${key}`, { count: doseQuantity ?? 1 }),
  value: key,
}));
```

Keep the `value` sent to React Hook Form stable and language-independent (`"tablet"`, `"drop"`, ...) — only the displayed `label` is translated/pluralized. Never store a translated string as the field's actual value.

# Verifying Translations

Resolving a translation key is pure JS — it does not require running the app on a device or in a browser. Sanity-check new keys (especially plural forms) with a small Jest assertion importing `t` from `@/i18n` rather than eyeballing the JSON or launching the app:

```ts
import { t } from "@/i18n";

expect(t("medications:doseUnits.tablet", { count: 2 })).toBe("Tablets");
```

# Anti-Patterns

Avoid:

- Any literal, hardcoded user-facing string in a component, screen, or constants file — labels, button text, placeholders, error messages, option lists, accessibility strings, all of it must come from `t()`.
- A namespace JSON file added to only one language (`en` or `es`), leaving the other to silently fall back.
- Flattened translation keys (`onboardingRegisterFormSexOptionsFemale`) instead of nested objects mirroring the screen/section structure.
- Calling `t()` at module scope for a label that must react to a changing value (language, `count`, any live form state) — module-level `t()` calls resolve once and never update.
- Storing a translated label as a form field's actual value instead of a stable, language-independent key.
- Defining `_one`/`_other` plural forms for a unit that never actually changes form (adds noise without benefit — a plain key is enough).
- Verifying a new/changed translation by launching the app instead of a quick Jest assertion against `t()`.

---

# Checklist

Before considering an i18n change — or any component/screen with user-facing text — complete, verify that:

- No literal user-facing string appears directly in the code; every one resolves through `t()`.
- The namespace JSON file exists under both `src/i18n/locales/en/` and `src/i18n/locales/es/`, with matching key structure.
- Both language `index.ts` files import and re-export the namespace.
- Components consume it via `useTranslation(namespace)` + `t("key")`; module-level constants use `t("namespace:key")` imported from `@/i18n`.
- Any label that depends on a live value (count, language) is computed inside a component's render, not cached in a module-level constant.
- Pluralized strings use `_one`/`_other` suffixes and are called with `t(key, { count })`.
- Field values sent to React Hook Form stay language-independent; only the displayed label is translated.
- New/changed keys are sanity-checked with a `t()` assertion, not just a manual app run.
