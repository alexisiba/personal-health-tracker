# Database (SQLite + Drizzle) Skill

## Purpose

This Skill defines how local persistence is structured in this project, using [`expo-sqlite`](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/) as the on-device database and [Drizzle ORM](https://orm.drizzle.team/) for typed access to it, so that every table/migration/query follows the same pattern instead of each feature inventing its own.

The app is local-only: everything lives in a single SQLite file on the device, with no sync/backend involved. Drizzle exists purely to give that local data typed schema + typed queries — not to talk to a remote database.

---

# File Structure

```
drizzle.config.ts        # drizzle-kit config: schema path, migrations out path, dialect, driver
babel.config.js           # adds the inline-import plugin so .sql migration files bundle as strings
metro.config.js           # tells Metro to resolve/bundle .sql files at all
src/db/
  schema.ts               # Drizzle table definitions (sqliteTable(...)) — the single source of truth
  client.ts                # the drizzle() client instance, wired to expo-sqlite
  migrations/              # generated by `npm run db:generate` — never hand-edited
    0000_xxx.sql
    migrations.js          # barrel the useMigrations hook imports; only emitted once schema.ts has ≥1 table
    meta/
      _journal.json
      0000_snapshot.json
```

`src/db/schema.ts` is the only file where tables are defined. Every other file (queries, the client, migrations) is generated from or reads from it — there is no second place that redefines a table's shape.

# Installing/Upgrading the Tooling

Always install `expo-sqlite` through Expo's own installer, never a plain `npm install`, so the version resolved matches the pinned Expo SDK instead of whatever npm's semver range picks:

```sh
npx expo install expo-sqlite
```

This also auto-registers the `expo-sqlite` config plugin in `app.json`'s `plugins` array — don't add it by hand.

For `drizzle-orm` and `drizzle-kit`, this project pins the **stable** npm dist-tag (`latest`), not the `@rc`/`@next`/`@beta` tags that Drizzle's own docs site examples sometimes show for the Expo SQLite guide:

```sh
npm install drizzle-orm@latest
npm install -D drizzle-kit@latest babel-plugin-inline-import
```

Check `npm view drizzle-orm dist-tags` / `npm view drizzle-kit dist-tags` before bumping either — grab the version under `latest`, not a pre-release tag, unless a specific feature genuinely requires the newer one.

# Defining a Table

Add it to `src/db/schema.ts` with `sqliteTable`. Follow the naming split already established there: **TypeScript field names are camelCase, actual SQL column names are snake_case**, passed explicitly as the column's first argument:

```ts
import { integer, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const users = sqliteTable("users", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  name: text("name").notNull(),
  lastName: text("last_name").notNull(),
  dateOfBirth: integer("date_of_birth", { mode: "timestamp" }).notNull(),
  sexAtBirth: text("sex_at_birth", { enum: SEX_AT_BIRTH_VALUES }).notNull(),
});
```

- **Primary key**: `integer("id").primaryKey({ autoIncrement: true })` — every table gets its own auto-incrementing `id`, not a shared/UUID scheme, unless a specific table has a reason not to.
- **Dates**: `integer("column_name", { mode: "timestamp" })` stores the value as Unix seconds and Drizzle maps it to/from a JS `Date` automatically. Don't store dates as `text` ISO strings.
- **Fixed value sets**: `text("column_name", { enum: [...] as const })` gives the column a TypeScript union type. This is a **compile-time-only** constraint — it does not add a SQL `CHECK`, so a raw/manual insert can still write an out-of-set value. Add a real `CHECK` constraint separately if runtime enforcement matters for that column.
- Keep the values behind an `enum` column in a named `const ... as const` array (see `SEX_AT_BIRTH_VALUES`) instead of inlining the array literal, so the same value set can be imported and reused (e.g. by a form's options list) instead of retyped.
- **Images/files**: store a local file URI as `text` (e.g. `profileImageUri: text("profile_image_uri")`, copied into a persistent app directory via `expo-file-system` after picking), never the raw bytes as a `blob`. SQLite isn't the place for file content — a blob column bloats the database file and is slower to read than just handing the UI a URI to render directly. Leave the column nullable unless the field is genuinely required to finish that flow.

# The Drizzle Client

`src/db/client.ts` opens the one on-device database file and wraps it with `drizzle()`:

```ts
import { drizzle } from "drizzle-orm/expo-sqlite";
import { openDatabaseSync } from "expo-sqlite";
import * as schema from "./schema";

const DATABASE_NAME = "personal-health-care.db";

const expoDatabase = openDatabaseSync(DATABASE_NAME, { enableChangeListener: true });

export const db = drizzle(expoDatabase, { schema });
```

Import `db` from `@/db/client` anywhere a query is needed (`db.select()...`, `db.insert()...`, or the relational `db.query.<table>.findMany()` API, unlocked because `schema` is passed in).

`enableChangeListener: true` is set so that [`useLiveQuery`](https://orm.drizzle.team/docs/connect-expo-sqlite#live-queries) (from `drizzle-orm/expo-sqlite`) can be used later for screens that should reactively update when the underlying rows change — it's not needed for one-off reads/writes.

**Only pass `{ schema }` once `src/db/schema.ts` actually exports at least one table.** `import * as schema from "./schema"` against a file with zero real exports trips this project's `import/namespace` ESLint rule — while the schema is genuinely empty, construct the client as `drizzle(expoDatabase)` instead.

# Generating Migrations

Never hand-write or hand-edit anything under `src/db/migrations/`. After changing `schema.ts`, regenerate it:

```sh
npm run db:generate
```

This runs `drizzle-kit generate` against `drizzle.config.ts`, which is configured with `driver: "expo"` specifically so the CLI also emits `src/db/migrations/migrations.js` — the barrel `useMigrations` imports at runtime, since the Expo JS bundle can't read migration files off disk the way a Node script could. That barrel is **only emitted once the schema has at least one table** — running `generate` against an empty `schema.ts` produces an empty `meta/_journal.json` and nothing else.

Commit everything `db:generate` produces (`.sql` files, `meta/`, `migrations.js`) — it's generated, but it's still the source of truth for what migrations ship, the same way a lockfile is committed.

# Bundling `.sql` Migration Files

Two config files make the generated `.sql` migration files importable from app code, and both are required together — either one missing breaks the build:

**`babel.config.js`** inlines each `.sql` file's contents as a string at build time (there's no filesystem to read them from at runtime):

```js
module.exports = function (api) {
  api.cache(true);
  return {
    presets: ["babel-preset-expo"],
    plugins: [["inline-import", { extensions: [".sql"] }]],
  };
};
```

**`metro.config.js`** tells Metro to resolve `.sql` as a bundleable extension at all (otherwise Metro ignores the import entirely):

```js
const { getDefaultConfig } = require("expo/metro-config");

const config = getDefaultConfig(__dirname);
config.resolver.sourceExts.push("sql");

module.exports = config;
```

# Running Migrations at Startup

Once `src/db/migrations/migrations.js` exists (see above — requires at least one table), wire it into the app root with the `useMigrations` hook, gating the app's UI behind success:

```tsx
import { db } from "@/db/client";
import migrations from "@/db/migrations/migrations.js";
import { useMigrations } from "drizzle-orm/expo-sqlite/migrator";

export default function RootLayout() {
  const { success, error } = useMigrations(db, migrations);

  if (error) return <Text>Migration error: {error.message}</Text>;
  if (!success) return null; // or a loading state

  return /* app content */;
}
```

This hook only needs to be wired once, at the app's root layout — not per-screen.

# Anti-Patterns

Avoid:

- Installing `expo-sqlite` with a plain `npm install` instead of `npx expo install expo-sqlite` — it can resolve a version that doesn't match the pinned Expo SDK.
- Installing `drizzle-orm`/`drizzle-kit` on a pre-release dist-tag (`@rc`, `@next`, `@beta`) without being asked to — this project pins the stable (`latest`) channel.
- Hand-editing any file under `src/db/migrations/` — change `schema.ts` and re-run `npm run db:generate` instead.
- A table field where the TypeScript name and the SQL column name are the same casing (e.g. `lastName: text("lastName")`) instead of camelCase → snake_case.
- Storing a date as `text` instead of `integer(..., { mode: "timestamp" })`.
- Trusting a `text(..., { enum: [...] })` column to reject invalid values at the database level — it's a TypeScript-only constraint.
- Passing `{ schema }` to `drizzle()` while `schema.ts` has no real exports yet (breaks the `import/namespace` lint rule).
- Adding/changing a `.sql`-file-bundling config in only `babel.config.js` or only `metro.config.js` — both are required together.
- Expecting `npm run db:generate` to emit `migrations.js` when `schema.ts` still has zero tables.
- Wiring `useMigrations` per-screen instead of once at the app's root layout.

---

# Checklist

Before considering a database change complete, verify that:

- The table/column lives only in `src/db/schema.ts` — no second place redefines its shape.
- Column names follow camelCase (TS) → snake_case (SQL), passed explicitly as the column's first argument.
- Every table has an auto-incrementing `id` primary key, unless there's a specific reason not to.
- Dates use `integer(..., { mode: "timestamp" })`, not `text`.
- A fixed value set lives in a named `as const` array and is passed to the column's `enum` option, not inlined.
- `npm run db:generate` was re-run after any `schema.ts` change, and its output is committed.
- `src/db/client.ts` passes `{ schema }` to `drizzle()` only if `schema.ts` has real exports.
- `babel.config.js`'s inline-import plugin and `metro.config.js`'s `sourceExts` are both still in place if either config file is touched.
