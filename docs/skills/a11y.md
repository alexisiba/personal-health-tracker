# Accessibility Skill

## Purpose

This Skill defines the accessibility standards that must be followed whenever creating new user interface components within this project.

Its purpose is to ensure that every component is accessible by default, using semantic native components, the platform's screen reader behavior (VoiceOver on iOS, TalkBack on Android), and minimal, well-implemented React Native accessibility props.

This Skill focuses exclusively on **component implementation** for a React Native / Expo mobile app.

Accessibility audits, testing procedures, and accessibility reviews belong to the Accessibility Review Skill.

---

# Core Principles

Accessibility is a core requirement.

Every new component should be accessible from its initial implementation rather than retrofitted later.

When making implementation decisions, prioritize:

- semantic native components (React Native Paper components, `Pressable`, `TextInput`, etc.)
- native platform behavior (VoiceOver / TalkBack, Dynamic Type, Reduce Motion)
- simplicity
- predictability

Accessibility should never depend on optional configuration.

---

# Semantic Components First

Always use the most semantic native component available.

Prefer:

- React Native Paper components (`Button`, `TextInput`, `Checkbox`, `RadioButton`, `Appbar`, `List.Item`, etc.), which already implement sensible accessibility defaults
- `Pressable` / `TouchableOpacity` with an explicit `accessibilityRole` when no Paper component fits
- `Text` for any readable content, so screen readers can find it

Do not build custom touchable containers when a semantic component already exists for the job.

Never recreate built-in platform behavior (buttons, switches, checkboxes, sliders) with a bare `View` and a gesture handler.

Examples:

Good:

```tsx
<Button mode="contained" onPress={save}>
  Save
</Button>
```

Avoid:

```tsx
<View onTouchEnd={save}>
  <Text>Save</Text>
</View>
```

---

# Native Platform Behavior

Preserve native platform behavior whenever possible.

Do not override default screen reader gestures or system accessibility settings unless absolutely necessary.

Avoid reimplementing functionality already provided by the platform or by React Native Paper, such as:

- buttons and icon buttons
- switches and checkboxes
- text inputs
- modals / dialogs
- pull-to-refresh and other system gestures

Prefer configuring native controls (via props) instead of replacing them with custom-drawn equivalents.

---

# Progressive Enhancement

Components should function with the minimum amount of custom logic required.

Layout and structure should come from React Native's component tree.

Styling should come from `StyleSheet` / theme tokens.

Custom gesture or animation logic should only add behavior on top of an already-usable component.

A component must remain operable by a screen reader user even if animations or custom gestures are disabled (e.g. Reduce Motion is on).

---

# Accessibility Props

React Native accessibility props (`accessible`, `accessibilityRole`, `accessibilityLabel`, `accessibilityState`, `accessibilityValue`, `accessibilityHint`) supplement semantic components.

They should never replace a component that already exposes correct behavior.

Before adding any accessibility prop, determine whether the underlying component (native or Paper) already provides the required role and state.

Use explicit accessibility props only when the component cannot express the necessary information on its own (e.g. a custom `Pressable`, an icon-only button, a custom gesture-based control).

Keep `accessibilityState` and `accessibilityValue` synchronized with the component's actual visual state.

Incorrect or stale accessibility props are worse than none at all.

---

# Touch and Focus Order

Every interactive component must be reachable and operable through the screen reader (VoiceOver / TalkBack), not only by touch.

Ensure:

- a logical screen reader navigation order that matches the visual reading order
- every interactive element is `accessible` and has an `accessibilityRole`
- touch targets are at least 44x44pt (iOS) / 48x48dp (Android); use `hitSlop` when the visual element is smaller
- no element traps screen reader focus or becomes unreachable
- custom gestures (swipe, long-press, drag) have an accessible alternative (e.g. an `accessibilityAction` or a visible button)

Do not require fine motor precision or multi-finger gestures to operate any core functionality.

---

# Focus Management

Components should preserve predictable accessibility focus behavior.

Move screen reader focus (`AccessibilityInfo.setAccessibilityFocus`) only when user interaction requires it, such as after opening a modal or showing a validation error.

Restore focus to a sensible element after temporary UI (modals, sheets, dialogs) closes.

Never let accessibility focus land silently on an unrelated or off-screen element.

Avoid unnecessary programmatic focus changes that disorient screen reader users.

---

# Component State

Visual state, internal state, and `accessibilityState` must always remain synchronized.

Examples include:

- `disabled`
- `selected`
- `checked`
- `expanded`
- `busy`

Screen reader users should receive the same state information as sighted users, announced automatically when the state changes.

---

# Images and Icons

Every meaningful `Image` or icon must include an `accessibilityLabel` that communicates its purpose.

Purely decorative images/icons must be hidden from the screen reader with `accessibilityElementsHidden` (iOS) and `importantForAccessibility="no"` (Android), or by wrapping them with `accessible={false}`.

Accessibility labels should communicate purpose, not visual appearance.

Avoid redundant wording such as:

- "image of"
- "icon of"

unless required for understanding.

Whenever an icon-only control (e.g. `IconButton`) performs an action, it must have an `accessibilityLabel` describing that action, since there is no visible text to fall back on.

---

# Forms

Every form control must have an accessible label, via the Paper component's `label` prop or an explicit `accessibilityLabel`.

Do not rely on placeholder text as the only label.

Communicate through accessibility props or live announcements:

- required fields
- validation messages (from Zod/React Hook Form)
- helper instructions
- field relationships (e.g. which error belongs to which input)

Use semantic form controls (`TextInput`, `Checkbox`, `RadioButton`, `AppSegmentedButtons`, `AppDropdown`, `AppDateInput`) whenever possible instead of custom-built equivalents.

---

# Headings and Content Structure

Use `accessibilityRole="header"` on `Text` elements that act as section titles, so screen readers can navigate by heading.

Heading hierarchy should reflect content structure, not visual size — do not skip levels of importance without reason.

Visual styling (font size, weight) belongs in the component's style, independent of its accessibility role.

---

# Screen Regions

On mobile, screen readers navigate linearly rather than by landmarks, but grouping still matters.

Use `accessible={true}` on a container to merge a group of elements into a single screen reader stop when they form one logical unit (e.g. a list item with a title and a subtitle).

Avoid over-grouping unrelated interactive elements into a single accessible container, since that hides individual controls from the screen reader.

---

# Lists and Tabular Data

Use `FlatList` / `SectionList` / Paper `List.*` components for any list of data.

Provide an `accessibilityLabel` per item that summarizes its content (e.g. "Ibuprofen, 400mg, 8:00 AM") rather than relying on the screen reader to read multiple fragmented `Text` nodes.

Never use tabular layouts purely for visual alignment without preserving the logical relationship between labels and values for screen reader users.

---

# Interactive Components

Interactive components should behave consistently with native platform controls.

Users should immediately understand, through the screen reader announcement or the visible UI:

- whether something is interactive
- its current state
- the available actions
- how to operate it (tap, double-tap, swipe)

Avoid surprising interactions, such as a `Pressable` with no visual affordance and no `accessibilityRole`.

---

# Modals and Dialogs

Modals and dialogs should:

- receive accessibility focus when opened
- set `accessibilityViewIsModal` (iOS) so the screen reader does not escape to background content
- restore focus to the triggering element when closed
- prevent interaction with background content while open

Prefer React Native Paper's `Dialog` / `Modal` components, which already implement most of this.

---

# Carousels and Swipeable Content

Carousels and swipeable views should:

- expose accessible next/previous controls, not only a swipe gesture
- identify the current slide/page via `accessibilityValue` (e.g. `{ text: "2 of 5" }`)
- avoid unexpected accessibility focus movement when the slide changes

Avoid autoplay unless it provides clear value, and always allow the user to pause it.

---

# Motion and Reduce Motion

Animations should improve usability, not decorate for its own sake.

Avoid excessive or fast movement.

Check `AccessibilityInfo.isReduceMotionEnabled()` and provide a reduced or instant alternative when the system setting is on.

Animations must never block or delay interaction with the underlying control.

---

# Responsive and Adaptive Accessibility

Accessibility requirements do not change across device sizes, orientations, or OS text-size settings.

Layouts must preserve:

- screen reader reading order
- accessibility focus order
- touch target sizes
- content availability

Support OS-level font scaling (Dynamic Type / font scale) by using relative units and avoiding fixed heights that clip enlarged text.

Never remove essential functionality on smaller screens without providing an accessible alternative (e.g. hiding a button behind an overflow menu is fine only if it stays reachable and labeled).

---

# Performance

Prefer lightweight accessibility solutions.

Favor:

- semantic Paper/native components
- built-in accessibility props
- native platform capabilities (VoiceOver, TalkBack, Dynamic Type, Reduce Motion)

Avoid heavy custom JavaScript workarounds (e.g. manually polling focus state) when a simpler native prop already solves the problem.

---

# Accessibility API

Components should expose an accessibility API that is simple, predictable, and difficult to misuse.

Whenever possible, components should compute their own `accessibilityLabel`, `accessibilityRole`, and `accessibilityState` internally, based on the props already passed to them.

Avoid requiring consumers to manually pass accessibility props that the component can determine automatically (e.g. deriving `accessibilityState={{ disabled }}` from an existing `disabled` prop).

Expose only the accessibility overrides that genuinely need customization (e.g. allowing a custom `accessibilityLabel` for context-specific wording).

---

# No Accessibility Props Is Better Than Wrong Ones

Never add accessibility props simply because accessibility is being considered.

If the underlying native or Paper component already provides the required role and state, use it as-is.

Only introduce explicit accessibility props when the component cannot express the required information on its own.

---

# Anti-Patterns

Avoid:

- pressable `View`s with no `accessibilityRole` and no `accessible` flag
- icon-only buttons with no `accessibilityLabel`
- missing or placeholder-only form labels
- touch targets smaller than 44x44pt / 48x48dp
- hidden or missing visual focus/pressed states
- stale `accessibilityState` that doesn't match the visual state
- duplicated or conflicting accessibility labels on nested elements
- color-only communication of state (e.g. only a red border for an error)
- unexpected accessibility focus movement
- gestures (swipe, long-press, drag) with no accessible alternative
- replacing a native or Paper component with a custom widget without justification

---

# Component Completion Checklist

Before considering a component complete, verify that:

- A semantic native or React Native Paper component has been used wherever possible.
- Native platform behavior (VoiceOver / TalkBack, Dynamic Type, Reduce Motion) has been preserved.
- Every interactive element is `accessible` with a correct `accessibilityRole`.
- Touch targets meet the minimum size (44x44pt iOS / 48x48dp Android).
- Screen reader focus behavior is predictable.
- Accessible labels exist where required, especially on icon-only controls.
- Accessibility props are minimal and correct.
- Images/icons have appropriate `accessibilityLabel`s, or are hidden when decorative.
- Forms expose proper labels and announce validation errors.
- Visual state and `accessibilityState`/`accessibilityValue` remain synchronized.
- The component does not introduce accessibility regressions on either iOS or Android.
